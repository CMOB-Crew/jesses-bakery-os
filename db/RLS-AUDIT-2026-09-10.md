# RLS audit — 10 September 2026

**Read this before touching anything in `db/migrations/`.** It is written for
whoever (person or agent) picks up the authorisation work next.

Audited 10 September against a throwaway Postgres 16 rebuilt from this
repository, plus the real `supabase/postgres` image for the Supabase-specific
facts. **Re-measured 11 September after merging main's migrations 092-096**
(`db/checks/rebuild-from-migrations.sh`: 93 applied, 3 skipped, 0 failed;
`db/checks/authorisation-tests.sh`: sections 2-4 pass, test 1 open as recorded).
Every number below is the 11 September measurement. Every claim was executed,
not inferred. The query that produced each one is included
so you can re-run it rather than trust it.

---

## Verdict first: do NOT "add RLS". It is already here, and it works.

Anyone skimming this repo and concluding "no RLS, let's add some" will waste a
week and probably weaken it. The measured state:

| Property | State |
|---|---|
| Base tables in `public` | 49 |
| RLS enabled | 49 of 49 |
| `FORCE ROW LEVEL SECURITY` | 48 of 49 |
| Tables with RLS on but zero policies (accidental deny-all) | 0 |
| Policies defined | 89 |
| `v_*` views with `security_invoker` on | 15 of 15 |
| `SECURITY DEFINER` functions with a pinned `search_path` | 6 of 6 |

The two things that most often make an RLS build silently useless are both done
correctly here:

- **Views are `security_invoker = on`** (migration 013). A `SECURITY DEFINER`
  view reads its base tables as the view's owner, so policies never fire and the
  view becomes a hole straight through RLS. All 15 are correct, including
  `v_driver_licence_days` from 095. One trap if you script this check: 095
  writes `security_invoker = true`, which Postgres stores as
  `security_invoker=true`, so a check that looks for the string `=on` flags a
  correct view. Read it with `pg_options_to_table(reloptions)` and cast to
  boolean.
- **Every `SECURITY DEFINER` function pins `search_path`**
  (`current_app_role`, `handle_new_user`, `jb_is_admin`, `jb_engine_health`,
  and 094's `jb_proof_objects` and `jb_proof_row_count`).
  An unpinned one is a privilege-escalation path: a caller sets `search_path` to
  a schema they control and your definer function calls their table.

### It was tested end to end, not just read

Same database, same query, three connections:

| Connection | `select count(*) from stores` |
|---|---|
| `jbo` — superuser, table owner | **84** |
| `jbo_app_test` — non-owner, `rolsuper=f`, `rolbypassrls=f`, no claims | **0** |
| `jbo_app_test` + valid admin claims | **84**, `current_app_role() = admin` |

`v_store_week` returned the same 0 / 84, which independently confirms
`security_invoker` is doing its job through the view layer. The model is sound.
Every finding below is about the wiring around it, not the policies themselves.

`db/AUTH-RLS-SETUP.md` is a correct design document. The problems are gaps
between that document and what actually ships.

## 1. HIGH (latent) — `DEPLOY.md`'s setup path bypasses every policy

**`DEPLOY.md` instructs a configuration in which none of the 89 policies do
anything.** Production is not in that configuration (`README.md` says so
directly; see "Is production affected?" below), so this is a hazard for the next
environment stood up from the docs (a staging project, a rebuild, the handover to
Jesse), not a live exposure.

`DEPLOY.md` step 1.4:

> Go to **Project Settings → Database → Connection string → URI**. Copy it and
> put your password in place of `[YOUR-PASSWORD]`. This is your `DATABASE_URL`.

That URI connects as Supabase's **`postgres`** role. Measured on the real
Supabase Postgres image:

```
rolname       | rolsuper | rolbypassrls
--------------+----------+-------------
postgres      | f        | t     <-- bypasses RLS
service_role  | f        | t     <-- bypasses RLS
authenticated | f        | f
anon          | f        | f
```

`rolbypassrls` is absolute. It is not something a policy can compensate for: the
row-security machinery is skipped entirely. Connect as `postgres` and all 49
tables, all 48 `FORCE` flags, all 89 policies, and the whole `runAsUser` /
`set_config('request.jwt.claims', …, true)` layer in `lib/db.ts` become
decoration. `AUTH_ENFORCED=1` still gates the *proxy* redirect, so the site
looks authenticated while the database returns every row to everyone.

That is exactly the first row of the table above: as a bypassing role, 84 stores
came back with no identity of any kind.

`db/AUTH-RLS-SETUP.md` step 5 already says the right thing — *"not the
`postgres` superuser"* — so the repo contradicts itself, and the doc people
actually follow is the one headed "Fast path — you click, I've made each step a
paste."

### Is production affected? No, and the project says so in writing

`README.md` (rewritten on main on 10 September) states it outright:

> | Auth | `AUTH_ENFORCED` is **on** — set in Netlify since 24 August. … |
> | Database role | The app connects as `jbo_app`, which does **not** bypass RLS. This is the "RLS flip" the 4 September runbook describes, and it has happened. |

The code agrees: `apps/web/app/api/feeds/mail-poll/route.ts:104` records RLS
refusing the cron's inserts in production, which cannot happen under a role that
bypasses RLS, and `db/migrations/004_the_app_role_grants_reconstructed.sql` reads
`jbo_app`'s grants off production.

So the fix below is for `DEPLOY.md` and every future environment.

**Two files contradict the README, both written on 10 September:**

- `db/migrations/092_a_driver_could_not_write_what_they_delivered.sql:6`:
  *"Both work today. Both stop working the moment AUTH_ENFORCED is turned on."*
- `db/checks/authorisation-tests.sh:192`: *"the app worked only because
  AUTH_ENFORCED is still off."*

They cannot all be true. If the README is right, those two comments are stale.
It also means the driver app's delivered-count and wastage writes were refused
in production for any period when that app code was deployed but 092 was not,
which matters when reading delivery data from those dates. If the comments are
right, the README's two rows are wrong. Whoever runs production should say which
one is true and correct the others. The "Prove it" query below answers the
database-role half in one second.

### The code-side fix (buildable and checkable from this repo)

Per the project rules in `CLAUDE.md`, a fix may not depend only on a dashboard
setting. The safe-either-way code change is a guard in `apps/web/lib/db.ts`:
when `AUTH_ENFORCED=1`, check once per cold start that `current_user` has
neither `rolsuper` nor `rolbypassrls`, and refuse to serve (throw with a message
naming the role) if it does. That turns this whole finding from a silent
misconfiguration into a boot failure nobody can miss. It is checkable locally:
point `.env.local` at the superuser with `AUTH_ENFORCED=1` and the app must
refuse; point it at a non-owner role and it must start. The remaining person
step is only the Netlify env value.

### Fix — run in the Supabase SQL editor as `postgres`

```sql
-- 1. The role the web app connects as. Not an owner, not a superuser,
--    no BYPASSRLS. NOINHERIT so it cannot pick up privileges via membership.
create role jbo_app login password '<strong-password>' noinherit;

grant usage on schema public to jbo_app;
grant select, insert, update, delete on all tables in schema public to jbo_app;
grant usage, select on all sequences in schema public to jbo_app;

-- Future tables too. Default privileges are per-granting-role: this only
-- covers objects created by the role that runs it, so run it as the same
-- role your migrations run as (postgres in the SQL editor).
alter default privileges in schema public
  grant select, insert, update, delete on tables to jbo_app;
alter default privileges in schema public
  grant usage, select on sequences to jbo_app;
```

Then set `DATABASE_URL` to **`jbo_app`'s** pooled connection string, not
`postgres`'s. Supavisor's transaction-mode username is `<role>.<project-ref>` —
so `jbo_app.abcdefgh…`, port `6543`. Confirm the exact host and port in Project
Settings → Database → Connection pooling.

`apps/web/lib/db.ts` already handles the pooler correctly (`prepare: false` for
non-local, SSL auto-on). No application code changes are needed for this — it is
purely which credential sits in the environment.

### The engine needs its own role, and it is the one that may bypass

The forecasting engine writes `store_reco` and `replenishment_plans` outside any
user's policies. Give it a separate credential — never reuse `jbo_app`, and
never let the web app use this one:

```sql
create role jbo_engine login password '<strong-password>' bypassrls;
grant usage on schema public to jbo_engine;
grant select, insert, update on replenishment_plans, store_reco to jbo_engine;
```

If the nightly run is driven by `pg_cron` (migration 045), a cron job executes as
the role that scheduled it. Schedule it as `jbo_engine`, or it runs as
`postgres` and quietly re-introduces a bypass path.

### Prove it, do not assume it

After switching the credential, run this **through the app's own connection**,
not the SQL editor:

```sql
select current_user,
       (select rolbypassrls from pg_roles where rolname = current_user) as bypasses_rls,
       (select rolsuper     from pg_roles where rolname = current_user) as is_superuser;
```

Required: `jbo_app`, `f`, `f`. Anything else and the audit fails.

## 2. HIGH — the authorisation tests do not exercise the app's claim mechanism

Condition 15's suite passes. It is testing something the application never does.

| Where | Setting written / read |
|---|---|
| `apps/web/lib/db.ts:64` and `:156` (the app) | writes `request.jwt.claims` — a JSON blob |
| `db/checks/ci-auth-stub.sql:20-22` (`auth.uid()`) | reads `request.jwt.claim.sub` |
| `db/checks/authorisation-tests.sh:50` (the tests) | writes `request.jwt.claim.sub` |

`request.jwt.claims` and `request.jwt.claim.sub` are two different settings. The
stub and the test agree with each other, so the suite is green — but neither
agrees with `lib/db.ts`, and **real Supabase reads `request.jwt.claims`**:

```sql
-- Supabase's actual auth.uid()
select ((current_setting('request.jwt.claims', true)::jsonb) ->> 'sub')::uuid;
```

This was found by accident: injecting claims the way `lib/db.ts` does returned
**0 rows** against the rebuilt database, and the same query with
`request.jwt.claim.sub` returned **84**.

To be precise about the risk, because it is easy to overstate: **the application
is correct and production is not exposed by this.** `lib/db.ts` writes the
format real Supabase reads. What is broken is the *evidence*. The suite that
exists to prove authorisation works is blind to the code path that implements
it — if someone changed the claims JSON key, dropped the `sub` field, or broke
`runAsUser`, CI would stay green. That is false confidence, which on a security
control is its own category of problem.

### Fix — make the stub mirror Supabase, then make the tests speak the app's language

In `db/checks/ci-auth-stub.sql`:

```sql
-- Mirror Supabase's real auth.uid(): read the JSON claims blob the
-- application actually sets, not a per-claim GUC nothing writes.
create or replace function auth.uid() returns uuid language sql stable as $$
  select nullif(nullif(current_setting('request.jwt.claims', true), '')::jsonb ->> 'sub', '')::uuid
$$;
```

The `true` on `current_setting` matters: an unset value must return null rather
than raise, so unauthenticated stays test 3's "returns nothing" instead of
becoming an error. The double `nullif` handles both "no claims at all" and
"claims present but no `sub`".

This exact statement was applied to the rebuilt database and re-tested: no
claims → **0 rows**; claims in the format `lib/db.ts` actually writes → **84
rows**, `current_app_role() = admin`. It is a drop-in replacement.

In `db/checks/authorisation-tests.sh:50`, replace the `set` with the JSON form
and, critically, use `set_config(..., true)` inside a transaction so the test
exercises the *transaction-local* property that `lib/db.ts` depends on:

```sql
begin;
select set_config('request.jwt.claims',
                  json_build_object('sub', '<uid>', 'role', 'authenticated')::text,
                  true);
-- assertions here
commit;
```

Add a fourth test while you are there: set claims transaction-locally, commit,
then re-query on the same connection and assert **zero rows**. That is Fred's
gotcha #1 — session-level claims leaking one user's identity onto the next
pooled request.

Good news, and the reason this is a regression guard rather than a bug report:
the property **holds today**, measured on the same connection —

```
inside tx   : stores=84
after commit: stores=0
```

`lib/db.ts` passes `true` to `set_config` in both places, so the identity dies
with the transaction exactly as designed. Nothing tests it, which means nothing
would notice if that `true` were ever dropped to `false` — a one-character
change that would leak one user's rows to the next request on a pooled
connection, with no error and no visible symptom.

## 3. HIGH — migration 065 exists only in production

`db/checks/rebuild-from-migrations.sh` skips three migrations by name. Two are
benign. The third is not:

> `065_secure_and_audit.sql` — needs `jb_plan_before_064`, which 064 creates by
> string-replacing a function read out of the LIVE database.

So the migration named *secure and audit* cannot be reproduced from this
repository. A rebuilt database is missing it and nothing says so at runtime.
This is the same class of problem migration 089 was written to fix, and it was
fixed for the engine but not for this.

**Fix, using the method 089 already proves works:** dump the real definitions
from production and commit them verbatim.

```sql
-- Run against production, save the output as a new migration.
select pg_get_functiondef(p.oid) || E';\n'
from pg_proc p
join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public'
  and p.proname in ('jb_plan_before_064')   -- add whatever else 064/065 touch
order by p.proname;
```

Commit as `091_065_reconstructed.sql`, make it `create or replace` /
`if not exists` throughout so it is a no-op against production, then delete the
`065_*` arm of `skip_reason()` in the rebuild script and confirm the run still
reports `failed 0`. Until that passes, "we can rebuild the database" is true of
the schema but not of the security hardening.

## 4. MEDIUM — `public.users` is the one table that does not FORCE RLS

```
relname | relrowsecurity | relforcerowsecurity
--------+----------------+--------------------
users   | t              | f
```

`FORCE` is what makes policies apply to the table's *owner*. Every other table
has it; the identity table — the one whose rows decide everyone else's access —
does not. It is not currently exploitable if the app never connects as the
owner, but that is precisely the property finding 1 shows is not guaranteed.

```sql
alter table public.users force row level security;
```

Then extend `db/checks/verify-rls-coverage.sh` to assert `relforcerowsecurity`
as well — today it only checks `relrowsecurity`, which is why this gap passed
CI unnoticed.

## 5. MEDIUM — condition 15, test 1: a driver can read another driver's run

This is the project's own finding, recorded at the bottom of
`.github/workflows/ci.yml`, repeated here because it is an authorisation gap and
belongs in an authorisation audit:

> 1. a driver cannot read another driver's run — **NOT MET**
> 2. a restricted role cannot write wrongly — met, five ways
> 3. an unauthenticated request returns nothing — met, every table

It is not a missing policy. There is no driver-to-run assignment in the data
model at all — every driver is shown every run and picks one — so no policy can
express "another driver's run". Closing it means building run assignment first:
a `run_assignments (run_id, driver_id, service_date)` table, then a policy on
the driver-facing reads keyed on `auth.uid()`.

Do not close this by widening the driver policy. The CI suite asserts the gap is
exactly the size it was measured to be, so it cannot widen unnoticed — keep that
assertion honest.

## 6. HARDENING — Supabase exposes `public` over PostgREST, and all 89 policies target every role

Two facts that combine:

- Supabase auto-publishes the `public` schema through PostgREST. Anyone holding
  the anon key — which ships to every browser and is not a secret — can query
  these tables directly over HTTPS without touching the Next.js app. RLS is the
  only thing standing there.
- All 89 policies are defined with no role restriction (`to public`), so they
  evaluate for `anon` and `authenticated` alike.

Today that is safe, because the policy expressions route through
`current_app_role()`, which resolves via `auth.uid()` and returns null for an
anonymous caller, so the `USING` clause is false and no rows come back. It fails
closed — the 0-row result in the verdict table above is that same mechanism. But
it fails closed by expression, with no second line of defence.

Add the grant layer as well:

```sql
revoke all on all tables in schema public from anon;
```

Check `apps/web/lib/supabase/` before also revoking `authenticated`.
`@supabase/ssr` is used here for auth session handling rather than data reads, so
it is probably safe — confirm rather than assume.

Consider narrowing new policies to `to authenticated` as they are written. It
costs nothing and removes anon from the evaluation path entirely.

## How this fits the project rules in `CLAUDE.md`

`CLAUDE.md` (added 11 Sep in `463d75b`) governs every change in this repo. Two
of its rules bear on this audit:

- **"Do not change the database schema without an explicit yes."** Findings 3,
  4, 5 and 6 are schema or privilege changes. Ask the project owner in plain
  words before applying any of them. Findings 1 (a doc correction and an app
  guard) and 2 (the test harness in `db/checks/`) change no schema.
- **Line 69 used to say row-level security "can only be exercised on the
  preview site". Corrected on this branch in `df82f9c`.** Sign-in needs the
  preview site; the policies do not. The rule, and the matching line in the
  `/perf-fixes` skill, now name both traps: a superuser connection bypasses
  every policy, and the stub's claim key (finding 2) returns zero rows for
  claims set the way `lib/db.ts` sets them. When finding 2 is fixed, delete the
  second trap from both files.

## What not to do

- **Do not disable RLS to debug a "no rows" problem.** Zero rows is this system
  failing closed, which is the design (`lib/db.ts`: *"fails closed, never
  silently wide open"*). Find the missing claim instead — and note from finding 2
  that "no rows" may mean you set the wrong claim key.
- **Do not point the app at `service_role`.** It has `rolbypassrls = t` and is
  strictly worse than `postgres`.
- **Do not add policies to `v_*` views.** Views cannot carry policies; they
  inherit from base tables via `security_invoker`, which is already on. Applying
  RLS thinking at the view layer produces confusion, not security.
- **Do not assume the demo build is covered.** `NEXT_PUBLIC_DEMO=1` deliberately
  keeps `AUTH_ENFORCED` unset and the site open. If the demo ever points at the
  production database, finding 1 turns from latent into an active breach. Keep it
  on its own Supabase project.
